## 从源码到原生程序

Carven 先确定一个程序的含义，再安排它的 C++ 实现。每个阶段都有自己的输入、输出和职责；后面的阶段使用已经检查过的事实。

<figure class="architecture-map">
  <ol class="architecture-pipeline">
    <li><span>01</span><strong>收集源码</strong><code>SourceBatch</code></li>
    <li><span>02</span><strong>建立语法树</strong><code>SyntaxProgram</code></li>
    <li><span>03</span><strong>检查与发布语义</strong><code>SemIRProgram</code></li>
    <li><span>04</span><strong>构造 C++ 结构</strong><code>TargetUnit</code></li>
    <li><span>05</span><strong>输出与原生构建</strong><code>C++ → 程序</code></li>
  </ol>
  <figcaption>编译器检查源语言契约并生成 C++；C++ 工具链负责原生编译、链接与优化。</figcaption>
</figure>

驱动收集源文件和 Crafts，形成一个闭合的源码批次，导入在这个批次内解析。前端建立语法树；语义分析完成声明和函数体，求解类型与失败集合，检查所有权及其他契约。成功后，后端接收只读的语义程序，生成可检查的 C++ 文件。

**C++ 仍负责它擅长的工作：** 原生重载与模板实例化、对象布局、优化和机器码。生成 C++ 之前的语义检查，与之后的原生编译各有边界。

## 展开看三个关键交接

<details class="architecture-detail">
<summary>语法树 → 语义程序：先完成事实，再交给后端</summary>

`ProgramDraft` 是可变的构建状态。它预留声明身份，支持前向引用和递归；完成声明与函数体后，求解类型和失败集合，再完成签名、声明和函数体。

发布前还要检查函数体契约、全局语义契约、所有权和局部指针空值事实。错误会阻止程序交付；警告可以随成功结果一同返回。

`SemIRProgram` 保存已确定的类型、结构化操作、存储关系与来源。后端不再查询 AST；源模板与完成的静态测试可以保留声明和来源，而不保留运行时函数体。后续阶段读取这些语义事实，建立自己的实现计划。

</details>

<details class="architecture-detail">
<summary>语义操作 → 静态执行或解释：共享机制，各有准入规则</summary>

常量初始化器、`const` 块、静态测试和解释执行使用共享的结构化语义执行器。执行器处理有类型的值、控制流和存储，并在资源预算内执行。

必需常量上下文只调用显式 `const fn` 及其允许的依赖。定义会接受执行能力检查；结果在发布时还要满足冻结与表示要求。例如，常量初始化构造的 `String` 可以冻结为具有稳定存储的 `str`。

解释器检查实际执行路径上的操作支持。它支持的是解释器子集，不能代替原生 C++ 调用和完整原生构建。共享操作不意味着几种执行方式拥有相同的准入范围。

</details>

<details class="architecture-detail">
<summary>语义程序 → C++：计划、准备、实现，最后才输出文本</summary>

`PlannedCompilation` 持有语义程序和对应的只读 `TargetPlan`。计划选择名字、接口、失败结果表示和产物安排。

`BodyPreparation` 借用已经发布的函数体事实，确定操作数需求与实现选择。`BodyRealizer` 将这些操作组合成目标结构，保留求值顺序、所需存储、清理和失败出口。已知结果并不能让有副作用的求值或可观察的生命周期消失。

完成的 `TargetUnit` 经过结构验证，汇总所需头文件、原生导入和产物依赖，之后 `emit` 才将它序列化为 C++ 文本。文件输出与原生编译是后续消费者。

</details>

## 几个值得留意的设计

| 要解决的问题                 | 编译器如何组织                                       | 对程序的意义                           |
| ---------------------------- | ---------------------------------------------------- | -------------------------------------- |
| 多层调用组合出不同失败       | 保留失败的类型身份与载荷，求解集合，检查恢复后的契约 | 恢复一个失败后，剩余责任仍然明确       |
| 读取、修改与转移具有不同要求 | 在语义操作中保留访问、存储和存活关系                 | 参数传递与清理依据已经检查过的关系生成 |
| 编译期特化会改变控制流       | 发布选定的静态分支、展开迭代和不同局部身份           | 后端沿普通存储与清理路径处理特化结果   |
| 已知值不一定允许删除计算     | 实现选择同时保留副作用、存储观察和生命周期           | 静态信息用于减少工作，并保持程序行为   |
| 用户需要知道错误来自哪里     | 源操作携带来源，隐式操作保留展开来源                 | 语言规则的诊断可以指向相应源码         |

这些职责分别属于语义构建、发布、执行或 C++ 生成。后端建立实现计划，不回写语义存储；运行库实现原生操作，不参与源码契约的求解。

## 同一条检查主线，几种命令出口

| 命令               | 在哪里完成工作                                           |
| ------------------ | -------------------------------------------------------- |
| `carven check`     | 成功的语义分析之后结束，包含所需常量执行与静态测试       |
| `carven interpret` | 分析后，将语义操作交给解释器执行                         |
| `carven compile`   | 分析后，规划并输出 C++ 产物                              |
| `carven main.cv`   | 生成 C++，与收集到的原生源文件一同编译、链接，再执行程序 |

源码收集、选项、文件输出、诊断呈现和进程启动由驱动负责。语义执行报告结构化结果；驱动决定如何将结果送到终端。词法和语法 dump 则直接消费相应的前端结果。
