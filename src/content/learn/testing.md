## Write a runtime test

Save totals.cv in the Carven repository root:

```carven
fn total(price: i32, count: i32) -> i32 => price * count;

test "line total" {
    check(total(12, 3) == 36);
    check(total(12, 0) == 0, "zero quantity");
}
```

Tests can share a module with functions or live in dedicated test files. Ordinary test is analyzed by compile, but a runner is not generated by default. Request test artifacts:

```sh
./xmakew run carven compile --tests=default -o generated totals.cv
```

This only generates C++. For this single-file example without main, continue from the same repository root:

```sh
clang++ -std=c++20 -Igenerated -Icrafts \
  generated/totals.cpp \
  generated/carven/generated/carven-test-main.cpp \
  -o generated/totals-tests
./generated/totals-tests
```

Use clang++ with support for the project's target runtime, specifying its full path if necessary. A passing test exits successfully. `-Igenerated` supplies generated interfaces and `-Icrafts` supplies runtime headers matching the compiler. Installed consumer projects use their installed Crafts location instead.

Link exactly one entry into a test executable. `--tests=default` does not remove source main, so this example declares no main. In other projects, separate the program entry from the functions under test and select the necessary implementation files. Native dependencies also need their providers and libraries. Registered tests in Carven's own repository run with commands such as `./xmakew test -g language`.

## check, require, and fail

A failed check reports and continues, suitable for independent assertions. A failed require stops the whole current test, suitable for a prerequisite of later code. fail always stops the current test. Messages are str or String; conditions must be bool.

Messages are evaluated eagerly, even when a condition succeeds. Do not put effects in a message that should only happen on failure. Test stopping propagates through synchronous Carven helpers and views, cleaning up locals. try cannot catch a test stop.

## Test recoverable failures

Append this to totals.cv, then repeat the generation, compilation, and execution commands above:

```carven
struct Invalid {}

fn positive(value: i32) -> i32 throw Invalid {
    if value <= 0 {
        throw Invalid {};
    }

    return value;
}

test "reject zero" {
    let rejected = try {
        positive(0)?;
        false
    } catch {
        Invalid(_) => true,
    };

    check(rejected);
}
```

test permits no residual escaping failure. This example checks both that a failure occurred and that the recovery arm was selected. A successful-input test must still handle failures declared by the contract, rather than assume the current input cannot fail.

## Read a diagnostic

Start with the original .cv location, then read the diagnostic code and explanation. Types, ownership, failure sets, C++ compilation, and linking are distinct boundaries. Native construction or provider errors may still occur after Carven analysis succeeds.

Use `_` for an intentionally unused value. Warnings do not fail an otherwise valid program. For native errors, inspect includes, provider signatures, and construction requirements; removing semantic checks is not a remedy.
